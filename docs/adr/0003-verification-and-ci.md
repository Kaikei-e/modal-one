# ADR-000003: 検証体制とCI

## コンテキスト

憲法は「公式スペックテストスイートの合格」と「wasmtimeとの差分テストの一致」を正しさの根拠と定めた。これを実際に回すハーネスの構成、wasmtimeとの接続方法、CI、および静的な安全性保証（unsafe禁止）を決める。

## 決定事項

### 1. spec-harnessの構成

- 公式のWebAssemblyスペックテストスイート（wast形式）をテスト入力とする。テストファイルはリポジトリにサブモジュールまたはベンダリングで取り込む。
- wastスクリプトのパースにはBytecode Allianceの`wast`クレートを用いる（器具であり、憲法第5条の借用範囲）。
- 対応するディレクティブは `assert_return`／`assert_trap`／`assert_invalid`／`assert_malformed`、およびモジュール登録と呼び出し（`register`／`invoke`）とする。未対応ディレクティブはスキップとして明示的に集計する。

### 2. 合格リスト方式による回帰検知

Phase 0の間、スペックテストの大半は未実装機能により失敗する。CIを意味のあるゲートにするため、**通過済みwastファイルの明示的なリスト（合格リスト）**をリポジトリで管理し、CIは合格リストの全件通過を必須条件とする。新しい命令範囲を実装するたびに、通過するようになったファイルを合格リストへ追加する。合格リストからの脱落（回帰）はCI失敗とする。

### 3. 差分テスト — wasmtimeの接続

wasmtimeは`spec-harness`の**dev-dependencyとしてライブラリ組み込み**する。同一モジュール・同一エントリポイント・同一引数での実行結果（戻り値またはトラップ種別）を、`modal-one-core`とwasmtimeの間で比較する。

- wasmtimeは実行パス（`modal-one-core`）の依存には一切現れない。
- 差分が出た場合、正はまず仕様書とスペックテストで判定する。wasmtimeは基準器であって仕様そのものではない。

### 4. CI

GitHub Actionsで、pushごとに以下を実行する。

1. `cargo fmt --check`
2. `cargo clippy`（warningをdenyに設定）
3. `modal-one-core`の単体テスト
4. spec-harnessによる合格リスト全件の実行
5. 合格リスト対象ファイルに対する差分テスト

リポジトリ作成済みのため、CIは最初のコミット（ワークスペース骨格）と同時に有効化する。

### 5. unsafeの静的禁止

`modal-one-core`のクレートルートに `#![forbid(unsafe_code)]` を課す。インタプリタ・デコーダ・バリデータはunsafeなしで実装可能であり、「サンドボックスの土台が安全なRustのみで書かれている」ことをコンパイラが機械的に保証する状態を保つ。

- `forbid`であり`deny`ではない。属性による局所解除は不可能とする。
- 解除（`deny`への緩和を含む）は、計測に基づく明確な理由を伴う将来のADRによってのみ行う。
- `kernel`クレートは本条の対象外とする。ベアメタル層でのunsafeの扱いはPhase 1着手時のADRで定める。

## 影響・トレードオフ

**得るもの**: 合格リスト方式により、CIが最初の1件から意味を持ち、回帰を機械的に検知できる。差分テストのライブラリ組み込みにより、結果を型付きで比較でき、トラップ種別まで突き合わせられる。forbid(unsafe_code)により、Phase 0の安全性主張が自己申告ではなくコンパイラの保証になる。

**受け入れるもの**: wasmtimeがdev-dependencyに入るため、spec-harnessのビルドは重い（実行パスのビルドには影響しない）。合格リストの手動管理には更新の手間が伴う。forbidにより、値スタック等で速度目的のunsafe技巧は使えないが、Phase 0の目的（正しさと学習）に照らして制約とみなさない。
