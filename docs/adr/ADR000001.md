# ADR-000001: Modal One 憲法 — プロジェクト定義と基本原則

- **ステータス**: Proposed
- **日付**: 2026-08-14
- **種別**: 正本（Constitution）。本プロジェクトで唯一の「正本」ADRであり、以後のADRはすべて通常ADRとする。

---

## コンテキスト

Modal Oneは、AIコーディングが主流となった時代に、作者が自分の手でコードを書くために始める長期プロジェクトである。出発点には三つの動機がある。

1. **手を取り戻す** — 約1年半、実装の大半をAIに委ねてきた。仕様を読み、設計し、一行ずつ書く行為そのものを回復したい。
2. **計算機科学を学ぶ** — 作者は文学部卒であり、CSを体系的に学んでいない。本プロジェクトの各段階を、形式意味論・計算機アーキテクチャ・OS・ABIといった領域の教科書と対にして進めることで、実装を伴うCS課程として機能させる。
3. **WebAssemblyを地に足のついた技術として理解する** — WASMの「安全な実行」「モジュラー性」「高速な立ち上がり」を、宣伝文句としてではなく、自分の実装と計測で検証可能な仮説として扱う。

技術的背景として、Wasmコア仕様は3.0のリリースにより大型機能の確定期を終え、システムインターフェース側（WASI / Component Model）はWASI 0.3が出て1.0の安定化に向かう時期にある。低層（コアインタプリタ）は凍った土台の上に手書きし、上層（WASI層）は薄く差し替え可能に保つことで、標準の成熟と本プロジェクトの進行を同期させる。

k23をはじめとする先行研究（Theseus、WALI、Mewz、wasmtimeのベアメタル対応等）の存在がこの構想の出発点にあり、本プロジェクトはその思想圏に連なる個人の学習実装である。

### ロードマップ見取り図（拘束力なし）

- **Phase 0**: no_stdのWasmコアインタプリタをホスト上で実装（デコーダ／バリデータ／実行器）
- **Phase 1**: QEMU riscv64 virt上のベアメタルへ移植（ブート・UART・アロケータのみのナノカーネル）
- **Phase 2**: WASI最小サブセットの自作実装。`wasm32-wasip1`でビルドしたゲストのHello World出力
- **Phase 3**: 複数WASMモジュール間のIPCと、サンドボックス境界コストの計測

進め方・ペース・順序の変更は自由であり、本ロードマップは目標宣言ではなく現時点の見取り図である。

## 決定事項

### 第1条（名称）

プロジェクト名は **Modal One** とする。表記は常に2語で用い、識別子・slugは `modal-one` とする。単語「Modal」単独では既存の著名プロダクトおよび一般名詞と衝突するため、単独表記は用いない。READMEおよび公開ドキュメントの冒頭には、検索可能性のため "wasm kernel" 等の識別語を必ず含める。

### 第2条（目的）

Modal Oneは、**WebAssemblyの検証可能性を唯一の隔離機構とする最小のカーネルを、作者が全行を理解している状態を保ったまま作る、学習のためのプロジェクト**である。

「作者が全行を理解している」ことを本プロジェクトの不変条件とする。成果物の完成度・速度・普及は、この不変条件に劣後する。

### 第3条（非目標）

以下を非目標として明示する。

1. **プロダクション利用** — Modal Oneを実運用に供することを目指さない。
2. **k23の代替** — k23および関連する先行研究は参考文献として敬意をもって参照する。ただし、競合としての名前の列挙（比較表・vs形式の記述等）は行わない。
3. **JIT** — 実行方式はインタプリタとする。JITコンパイルは本憲法の有効期間において目指さない。
4. **実機ハードウェアのサポート** — 基準環境はQEMU virt（riscv64）とし、物理ボード・デバイスドライバの対応は行わない。ただし本項はISAには適用されない。RISC-V ISA自体は本プロジェクトの中心的な対象である（第7条）。

### 第4条（将来目標として保持するもの）

**SMP（マルチコア対応）は非目標としない。** 初期実装はシングルコア前提で進めるが、マルチコア・メニーコアが標準となった時代において、その可能性を最初から放棄することは本プロジェクトの趣旨に反する。シングルコア前提が構造に深く刻まれる設計判断を行う場合は、該当箇所をADRに記録し、将来のSMP化の際に見直すべき地点を追跡可能にしておく。

### 第5条（借りる／作るの境界線）

判定基準は「**それは実行パスか、器具か**」である。

- **手書きする（実行パス）**: バイナリデコーダ（LEB128を含む）、バリデータ、インタプリタ本体、カーネル（ブート・メモリ管理・割り込み）、WASI実装。実行パスでは外部の実装クレート（wasmparser等）を使用しない。
- **借りてよい（器具）**: 公式スペックテストスイートおよびそのハーネスで用いるwastパーサ、ゲストプログラムを生成するツールチェーン（rustcの`wasm32`ターゲット等）、CI・ビルド補助、そしてwasmtime本体 — wasmtimeは**差分テストの基準器（オラクル）**および**設計の参照（教科書）**として用いる。

境界の判断に迷った場合は、上記の判定基準に立ち返り、必要ならADRで判断を記録する。

### 第6条（AI利用）

AI利用の目的は第2条の不変条件（作者が全行を理解している状態）を守ることであり、その範囲内での利用方法は**作者の裁量に委ねる**。

原則として、実行パスの実装コードは作者が自分の手で書く。仕様や概念の解説、設計の壁打ち、書いたコードのレビュー、デバッグの支援、器具側コードの生成、ドキュメントの共同執筆にAIを用いることは自由である。細則・記録義務・脱出手続きは定めない。

### 第7条（技術的基盤）

憲法レベルで確定する技術的事項は以下に限る。

1. **no_std** — 実行パスは`core`および`alloc`のみに依存する。この制約はPhase 0の初日から適用する。
2. **ターゲット** — 基準ターゲットはriscv64（QEMU virtマシン）とする。
3. **正しさの二本柱** — 公式スペックテストスイートの合格と、wasmtimeとの差分テストの一致をもって正しさの根拠とする。
4. **仕様の採用方針** — WasmコアはWasm 1.0（MVP）相当のサブセットから実装を開始し、2.0/3.0の機能（末尾呼び出し、例外処理等）は個別のADRにより選択的に採用する。
5. **層の分離** — WASI／Component Model層はコアから分離し、薄く差し替え可能に保つ。WASIはp1相当の最小サブセットの手書きから始め、Component Model対応は独立したフェーズとして扱う。

クレート構成の初期案（`modal-one-core`／`spec-harness`／`kernel`／`xtask`）を含む実装詳細は、ADR-000002以降で定める。

### 第8条（改正手続き）

本ADRは直接編集しない。憲法の改正は、**正本ではない新規の通常ADR**によって行う。改正ADRには、対象となる条項、変更内容、変更理由を明記し、本ADRとのsupersedes関係を記録する。

### 第9条（公開とライセンス）

リポジトリは公開とする（作成済み）。READMEおよび公開文書では誇大な表現を避け、実装の現状を正確に記述する。

ライセンスは **MIT OR Apache-2.0（デュアルライセンス）** とする。

## 影響・トレードオフ

**得るもの**: 手書きの実装力の回復。仕様読解を通じた形式意味論・アーキテクチャ・OS・ABIの体系的学習。WASMの主要な主張（安全性・モジュラー性・起動速度）に対する、自分の実装と計測に基づく一次的理解。長期にわたり心理的に持続可能な、締切も競合もないプロジェクト。

**受け入れるもの**: 進捗は遅い（手書きと学習優先のため。半年〜年単位を前提とする）。実行速度はwasmtime等の実用ランタイムに遠く及ばない（インタプリタ方式・学習目的のため、これを問題としない）。シングルコア前提で進めるため、将来SMP化する場合に一定の再設計が生じうる（第4条の記録により影響範囲を追跡する）。標準（WASI／Component Model）は進行中であり、上層の設計は将来変更されうる（第7条5項の層分離により影響を局所化する）。
