# ADR-000002: クレート構成・実装順序・実行表現

- **更新日**: 2026-11-15（ロードマップレビューを受けて決定2・3・4・6を改訂し、決定7・8を追加）

## コンテキスト

憲法はno_std・RISC-Vターゲット・正しさの二本柱・Wasm 1.0サブセットからの開始を定めたが、Phase 0のコードを書き始めるには、ワークスペースの形、命令をどの順で実装するか、そして実行器の内部表現という3つの決定が必要である。特に実行表現は、素直なIR方式と、Titzerが提示したin-place方式（生バイト列の直接解釈）のどちらを取るかで、Phase 0全体の構造が変わる。

## 決定事項

### 1. ワークスペース構成

Cargoワークスペースを以下の4クレートで構成する。

| クレート | 役割 | 制約 |
|---|---|---|
| `modal-one-core` | 実行パス: デコーダ／バリデータ／インタプリタ | `no_std`（`core` + `alloc`のみ） |
| `spec-harness` | 公式スペックテスト駆動と差分テスト | `std`可。器具（憲法第5条） |
| `kernel` | Phase 1以降のベアメタル層 | 当面は空 |
| `xtask` | ビルド・開発補助 | `std`可。器具 |

### 2. crates.io

当面登録しない。空パッケージによる名前予約は行わない。Phase 0で動くもの（最初のスペックテスト合格）ができた時点で、`modal-one-core`を公開する。最初の公開版の番号は、公開時点の `Cargo.toml` の値に従う（ワークスペース骨格は cargo の既定値 `0.1.0` で作られている）。当初案の「0.0.1として公開」は取り下げる。未公開の間、この番号は意味を持たないためである。`spec-harness`・`kernel`・`xtask`は公開対象外とする。

なお`modal-one`および周辺名は2026-08-14時点でcrates.io未登録であることを確認済み。

### 3. 実装順序 — 縦切り

横切り（全セクションのデコード完成→検証→実行）ではなく、縦切り（デコード→検証→実行を最小の命令範囲で貫通させ、以後範囲を広げる）を採用する。

**最初のマイルストーン**: `(module (func (export "answer") (result i32) i32.const 42))` をデコード・検証・実行し、spec-harness経由でassert_returnを1件通過させる。

以後の拡張順序（目安であり、順序の入れ替えは通常の裁量で行ってよい）:

1. i32/i64の数値命令
2. locals・parametric命令（`drop`／`select`）
3. 制御フロー（`block`／`loop`／`if`／`br`／`br_if`／`br_table`）
4. 関数呼び出し（`call`）と必要最小限のimport/export処理
5. 線形メモリ（`load`／`store`／`memory.grow`）
6. `table`と`call_indirect`
7. `global`
8. f32/f64（NaN正規化を含む）

浮動小数点を最後に置くのは、NaN関連のスペックテストが厳格で初期の泥沼になりやすいためである。整数と制御フローで実行器の骨格を固めてから着手する。後回しにするのは浮動小数点の演算命令である。値の表現（決定6）と `f32.const`／`f64.const` のデコードは、整数命令を広げる段階で先に入れる。表現を後から変えると、それまでに書いた全命令に手戻りが出るためである。

### 4. 実行表現 — in-place方式

IRへの変換も内部バイトコードへの書き換えも行わず、**デコード・検証済みの生のWasmバイト列を直接解釈する**（Titzer方式）。分岐の解決には、バリデータが検証の副産物として生成する**サイドテーブル**（分岐ごとの命令ポインタ差分とスタック調整量を記録した補助表）を用いる。

採用理由: 変換レイヤを持たないため実行器と仕様の対応が1対1になり、モジュールごとの追加メモリがサイドテーブルのみで済む。この特性はPhase 1以降のカーネル用途（省メモリ・起動即実行）と整合する。先行研究（Titzer, OOPSLA 2022）とその実装（Wizardエンジン）が一次資料として存在する。

サイドテーブルのエントリ構造（ip差分・スタック高さ調整・アリティ等のフィールド設計）は実装過程で確定し、設計が固まった時点で別ADRに記録する。出発点は論文（[arXiv:2205.01183](https://arxiv.org/abs/2205.01183) §3.1）の4つ組 `⟨Δip, Δstp, valcnt, popcnt⟩` である。論文がエントリを持つと列挙するのは `br`／`br_if`／`br_table` と `else` の暗黙の分岐であり、`block`／`loop`／`end`／`return` は分岐バイトコードではないとする。`if` は論文の列挙に無いが、条件が偽のときに `else` 側へ飛ぶためのエントリを要する。`br_table` は、`maxcase` を持つ先頭エントリの後ろにラベル数+1 個のエントリを並べる（論文 Listing 1）。

論文の実装（Wizard）と Modal One には、次の意図的な違いがある。

| 項目 | 論文（Wizard） | Modal One |
|---|---|---|
| スタック溢れの検出 | ガードページと OS のシグナル | 明示的な深さ検査（決定7の上限を超えたら trap） |
| 値スタックの要素 | unboxed。型タグは GC 用で、実行時の検査には使わない | タグ付き enum（決定6）。目的は読みやすさと `forbid(unsafe_code)` の維持 |
| ディスパッチ | 主要部は手書きアセンブリ | Safe Rust の `match` |

### 5. バリデータの位置づけ

最初の縦スライスからバリデータを含める。実行は検証を通過したモジュールに対してのみ行い、「未検証実行」の開発フェーズを設けない。サイドテーブルが検証の副産物である以上（決定4）、検証パスは実行の前提として常設される。

### 6. 値とトラップの表現

- 値スタックはタグ付きenum（`Value::I32(i32)` 等）から始める。タグなし表現（生u64）への最適化は、計測とセットで将来のADRとして扱う。
- **浮動小数点はビット列で保持する**。`Value::F32(u32)`／`Value::F64(u64)` とし、算術の直前にだけ `from_bits` で `f32`／`f64` に戻す。理由は3つある。
  1. `abs`／`neg`／`copysign`／`reinterpret`／`load`／`store` が整数のビット演算になり、NaN ペイロードの保存が自明になる。
  2. Rust は NaN のビットパターンを保証しない。ビット列で持てば、ホスト（SSE2）とベアメタル（soft-float）の差を自分の層で吸収できる。
  3. 差分テストで NaN を分類して比べられる（[ADR-000003](0003-verification-and-ci.md) 決定3）。
- 浮動小数点の算術結果が NaN のときは、正の canonical NaN（f32 は `0x7fc0_0000`、f64 は `0x7ff8_0000_0000_0000`）を返す。これは通常の規則（入力の NaN がすべて canonical なら結果も canonical、そうでなければ任意の arithmetic NaN）の許す範囲に入り、Wasm 3.0 の決定論的プロファイルの規則（浮動小数点命令が生成する NaN は正の canonical）とも一致する。`neg`／`abs`／`copysign` は符号ビットだけを操作し、ペイロードを書き換えない。
- 2026-11-15 時点の `modal-one-core/src/lib.rs` は `F32(f32)`／`F64(f64)` である。ビット列への変更は、最小のバリデータと実行器を置く段階で作者が行う。
- トラップおよびデコード・検証エラーは`Result`で伝播する。no_std環境（panic=abort）ではpanicの捕捉ができないため、実行パスでのpanicはバグとして扱う。これを機械的に確かめる lint とファジングは [ADR-000003](0003-verification-and-ci.md) 決定6・7で定める。

### 7. 実装定義の資源上限

仕様の付録（Implementation Limitations）は、実装が資源に上限を設けることを認めている。Modal One は上限を一箇所にまとめる。

- 上限は1つの `Limits` 構造体に定数として置く。対象は、値スタックの深さ、呼び出しフレーム数、ローカル数、関数本体のバイト数、制御ネストの深さ、線形メモリの最大ページ数、テーブルの最大要素数とする。具体的な値は実装時に決め、この ADR に追記する。
- デコード時・検証時の超過は専用のエラーに、実行時の超過は trap（資源枯渇）に写す。無限再帰のテストが `assert_exhaustion` として通ることを、直接呼び出し（`call`）を入れる段階の合格条件にする。
- モジュールが申告するサイズに基づく確保には `try_reserve`／`try_reserve_exact` を使い、失敗は資源上限のエラーに写す。`Vec::with_capacity` は、容量の桁あふれで panic し、確保失敗で `handle_alloc_error` に回る（`no_std` + `alloc` の既定は panic）ため、この用途には使わない。

### 8. Module・Instance・Store の3層

不変の定義である Module、添字の対応を持つ Instance、実体（線形メモリ・テーブル・グローバル）を持つ Store の3層を、最初の実行器を置く段階で型として先に置く。中身はその時点で必要な分だけでよい。`table`／`global`／`import` を入れる段階で初めて導入すると、それまでに書いた全ハンドラのシグネチャが変わるためである。

## 影響・トレードオフ

**得るもの**: 縦切りにより、最初の動作確認（assert_return 1件）まで到達する時間が最短になり、以後は常に「動く状態」を保ったまま命令範囲を広げられる。in-place方式により、実行器の構造がカーネル用途の要件（省メモリ・変換レイヤなし）と最初から一致する。

**受け入れるもの**: in-place方式は、素直なIR方式に比べて最初の貫通が重い。構造化制御フロー（`block`/`if`/`else`/`end`の対応関係と分岐先解決）をサイドテーブル設計として最初に解かなければならず、これがPhase 0最初の本格的な設計問題になる。IR方式で一度書いてから移行する学習ステップは省略するため、詰まった場合の後退先は「参照資料（論文・Wizard実装）を読む」ことになる。また、縦切り＋float後回しのため、スペックテスト全体の合格率は中盤まで低い水準で推移する（これを問題としない）。
