# ADR-000002: クレート構成・実装順序・実行表現

## コンテキスト

憲法はno_std・RISC-Vターゲット・正しさの二本柱・Wasm 1.0サブセットからの開始を定めたが、Phase 0のコードを書き始めるには、ワークスペースの形、命令をどの順で実装するか、そして実行器の内部表現という3つの決定が必要である。特に実行表現は、素直なIR方式と、Titzerが提示したin-place方式（生バイト列の直接解釈）のどちらを取るかで、Phase 0全体の構造が変わる。

## 決定事項

### 1. ワークスペース構成

Cargoワークスペースを以下の4クレートで構成する。

| クレート | 役割 | 制約 |
|---|---|---|
| `modal-one-core` | 実行パス: デコーダ／バリデータ／インタプリタ | `no_std`（`core` + `alloc`のみ） |
| `spec-harness` | 公式スペックテスト駆動と差分テスト | `std`可。器具（憲法第5条） |
| `kernel` | Phase 1以降のベアメタル層 | 当面は空 |
| `xtask` | ビルド・開発補助 | `std`可。器具 |

### 2. crates.io

当面登録しない。空パッケージによる名前予約は行わない。Phase 0で動くもの（最初のスペックテスト合格）ができた時点で、`modal-one-core`を0.0.1として公開する。`spec-harness`・`kernel`・`xtask`は公開対象外とする。

なお`modal-one`および周辺名は2026-08-14時点でcrates.io未登録であることを確認済み。

### 3. 実装順序 — 縦切り

横切り（全セクションのデコード完成→検証→実行）ではなく、縦切り（デコード→検証→実行を最小の命令範囲で貫通させ、以後範囲を広げる）を採用する。

**最初のマイルストーン**: `(module (func (export "answer") (result i32) i32.const 42))` をデコード・検証・実行し、spec-harness経由でassert_returnを1件通過させる。

以後の拡張順序（目安であり、順序の入れ替えは通常の裁量で行ってよい）:

1. i32/i64の数値命令
2. locals・parametric命令（`drop`／`select`）
3. 制御フロー（`block`／`loop`／`if`／`br`／`br_if`／`br_table`）
4. 関数呼び出し（`call`）と必要最小限のimport/export処理
5. 線形メモリ（`load`／`store`／`memory.grow`）
6. `table`と`call_indirect`
7. `global`
8. f32/f64（NaN正規化を含む）

浮動小数点を最後に置くのは、NaN関連のスペックテストが厳格で初期の泥沼になりやすいためである。整数と制御フローで実行器の骨格を固めてから着手する。

### 4. 実行表現 — in-place方式

IRへの変換も内部バイトコードへの書き換えも行わず、**デコード・検証済みの生のWasmバイト列を直接解釈する**（Titzer方式）。分岐の解決には、バリデータが検証の副産物として生成する**サイドテーブル**（分岐ごとの命令ポインタ差分とスタック調整量を記録した補助表）を用いる。

採用理由: 変換レイヤを持たないため実行器と仕様の対応が1対1になり、モジュールごとの追加メモリがサイドテーブルのみで済む。この特性はPhase 1以降のカーネル用途（省メモリ・起動即実行）と整合する。先行研究（Titzer, OOPSLA 2022）とその実装（Wizardエンジン）が一次資料として存在する。

サイドテーブルのエントリ構造（ip差分・スタック高さ調整・アリティ等のフィールド設計）は実装過程で確定し、設計が固まった時点で別ADRに記録する。

### 5. バリデータの位置づけ

最初の縦スライスからバリデータを含める。実行は検証を通過したモジュールに対してのみ行い、「未検証実行」の開発フェーズを設けない。サイドテーブルが検証の副産物である以上（決定4）、検証パスは実行の前提として常設される。

### 6. 値とトラップの表現

- 値スタックはタグ付きenum（`Value::I32(i32)` 等）から始める。タグなし表現（生u64）への最適化は、計測とセットで将来のADRとして扱う。
- トラップおよびデコード・検証エラーは`Result`で伝播する。no_std環境（panic=abort）ではpanicの捕捉ができないため、実行パスでのpanicはバグとして扱う。

## 影響・トレードオフ

**得るもの**: 縦切りにより、最初の動作確認（assert_return 1件）まで到達する時間が最短になり、以後は常に「動く状態」を保ったまま命令範囲を広げられる。in-place方式により、実行器の構造がカーネル用途の要件（省メモリ・変換レイヤなし）と最初から一致する。

**受け入れるもの**: in-place方式は、素直なIR方式に比べて最初の貫通が重い。構造化制御フロー（`block`/`if`/`else`/`end`の対応関係と分岐先解決）をサイドテーブル設計として最初に解かなければならず、これがPhase 0最初の本格的な設計問題になる。IR方式で一度書いてから移行する学習ステップは省略するため、詰まった場合の後退先は「参照資料（論文・Wizard実装）を読む」ことになる。また、縦切り＋float後回しのため、スペックテスト全体の合格率は中盤まで低い水準で推移する（これを問題としない）。
